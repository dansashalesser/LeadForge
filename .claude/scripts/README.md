# scripts/

Utility scripts used by the harness. Python scripts are stdlib-only except where a package is listed in `setup/harness-requirements.txt` — those import from the harness-owned venv at `<harness root>/.venv-tools`, never from a target repo's environment. A target repo's venv belongs to its owner and can be pruned or relocked at any time; anything the harness depends on there dies silently when that happens.

## Setup & Stack

| Script | Purpose |
|---|---|
| `generate-project-stack.sh` | Auto-detect project language, runtime, package manager, deps, test commands, Docker services → writes `PROJECT_STACK.md`. Called by `install.sh` and `update.sh` automatically. |
| `setup/check-settings-json.sh` | Strict-JSON validation for one or more settings files/templates (`check-settings-json.sh <file> [<file> ...]`). Exit 1 if any file is unparseable, naming the line and column. Claude Code parses `.claude/settings.json` as strict JSON — no comments, no content after the closing brace — and silently ignores a malformed file, so every permission rule and hook in it stops working. `install.sh` runs it on `templates/settings.json.template` before copying; `update.sh` runs it on the regenerated harness settings plus the per-project template; `/kiro:harness-validate` runs it as a blocking step. No-ops with a warning if `python3` is absent. |
| `setup/repair-settings-json.py` | Repairs a project's `.claude/settings.json` broken by a trailing `//` comment block (shipped by the pre-2026-08-12 template): peels the block into `.claude/settings.notes.md` and leaves valid JSON behind. Idempotent — valid files report `OK` and are untouched; anything not fixable by removing a trailing comment block is reported `MANUAL` rather than guessed at. `repair-settings-json.py <project_dir> [...]`, `--dry-run` to preview. Run on every `install.sh` and `update.sh`, and on **every session start** by `hooks/claude/session-start-hook.sh` (which locates it via `$HOME/.sdd-harness-root` and prints `[SETTINGS-REPAIRED]` only when it actually changed something) — so a settings file broken by an old install costs one session instead of lasting until someone runs `update.sh`. |
| `setup/check-harness-deps.sh` | **The dependency guard.** Verifies, heals, and declares every package the harness relies on, then reports each one as `ok` / `healed` / `FAILED` / `skipped`. Two manifests drive it: `setup/harness-requirements.txt` installs into the harness-owned `.venv-tools` (no target repo has these, so no target repo can prune them), and `setup/repo-requirements.txt` installs into each registered repo's venv **and** declares it in that repo's own manifest via `setup/declare-repo-deps.py`. Declaration is the half that makes it stick: `raindrop-setup.sh` and `headroom-setup.sh` used to `pip install <pkg> -q 2>/dev/null` into repo venvs and write nothing to the repo's manifest, so the package looked like an orphan and the repo's next `uv sync` / lockfile regen / dependency prune deleted it — while the swallowed output meant the harness printed "Done." either way. Run by `install.sh` and `update.sh` *before* `raindrop-setup.sh` (whose auto-instrument pass needs the SDK present). Also reports machine-level tooling that no repo can declare: whether the `headroom` binary is resolvable (including when its directory is off PATH), whether the proxy is listening, and whether `ANTHROPIC_BASE_URL` routing is wired — flagging the one dangerous combination, routing pointed at a proxy that refuses the connection. It distinguishes curl exit 7 (nothing listening → real failure) from 28 (listening but slow → fine), because collapsing the two reports a false outage on a healthy machine. `SDD_DEP_CHECK_ONLY=1` reports drift without changing anything; `SDD_SKIP_DEP_DECLARE=1` installs but never touches repo manifests. Exit 1 if anything could not be healed. |
| `setup/harness-requirements.txt` | Packages the harness itself imports → installed into `.venv-tools`. Format: `<pip-spec> [import-name]`. Add a line here rather than importing from whatever `python3` a target repo happens to provide. |
| `setup/repo-requirements.txt` | Packages that must import inside a **target repo's** interpreter (currently `raindrop-ai`, which instruments the repo's own source). Installed *and* declared in that repo. Everything the harness merely calls for itself belongs in `harness-requirements.txt` instead. |
| `setup/declare-repo-deps.py` | Idempotently declares packages in a target repo's manifest: `pyproject.toml` → `[dependency-groups] harness = [...]` (PEP 735), else `requirements.txt` → `requirements-harness.txt` plus a `-r` reference. Repos with neither are skipped as non-Python. Validates the result with `tomllib` and restores the original rather than leaving a broken manifest. Called by `check-harness-deps.sh`; usable standalone as `declare-repo-deps.py <repo> <pkg-spec> [...]`. |
| `setup/reconcile-settings-templates.py` | **Owns the relationship between the two settings templates.** `templates/settings.json.template` ships to every installed project; `templates/settings.harness.json.template` generates the harness repo's own `.claude/settings.json`. They had silently diverged — as of 2026-08-30 the harness template was missing 14 hook registrations the project template carried, and held 4 it did not, so those 14 hooks fired in every installed repo and **not** in the repo where they are written and tested (including the whole tool-failure-memory loop). Enforces `hooks(harness) == hooks(project) + HARNESS_ONLY`, where `HARNESS_ONLY` is an explicit allowlist and each entry carries a written reason (currently one: `address-check-hook.sh`, which enforces a convention present only in the harness's own CLAUDE.md). `--check` reports drift and exits 1 — run by `/kiro:harness-validate`; `--sync` regenerates the harness template from the project one and is run by `install.sh` and `update.sh` *before* either copies a template anywhere. Idempotent. **Permissions are deliberately excluded**: the two files *should* differ there, since the harness grants itself write access to its own source tree that no target project may have, and denies `git push*` where projects only deny force-push. The workflow is add-to-project-template-then-`--sync`; editing the harness template directly is the drift the check catches. |
| `setup/gitnexus-reconcile.sh` | Keeps GitNexus's managed `CLAUDE.md` (or `AGENTS.md`, for projects that relocated their conventions there — `CLAUDE.md` wins on a tie) block honest about what is actually wired. `--wire` registers the `gitnexus` MCP server — writing it into `.mcp.json` and adding it to `enabledMcpjsonServers` in `.claude/settings.json` via `setup/gitnexus-mcp.py` (used by `install.sh --with-gitnexus`, replacing the old "paste this JSON yourself" note); `--check` exits 0 only when both the `.gitnexus/` index and the MCP server exist, gating whether `gitnexus setup` is allowed to write its MUST/NEVER block at all; with no flag it reconciles — stripping the block when it is dead, and when it is live **compacting** it (`compact_block`) plus repairing its skill paths and rewriting any bare `gitnexus_*` tool names to the `mcp__gitnexus__*` form the MCP server actually exposes. Compaction replaces the upstream block body (~900 tokens on every API call: each rule written twice in MCP and CLI form, plus a resources table and a skill-path table the skill listing already carries) with the harness's own rule set, which keeps every MUST/NEVER rule and states the CLI fallback once. The indexed repo name is carried over from the existing block (it is GitNexus's registry name, not always the directory name), falling back to the directory name; an unterminated block (no `<!-- gitnexus:end -->`) is left alone rather than spliced. Idempotent — set `SDD_GITNEXUS_FULL_BLOCK=1` to keep the upstream block untouched. Run by `install.sh` around `gitnexus setup` and by `update.sh` on every sync (non-fatal), because the block is committed while `.gitnexus/` is gitignored and the MCP server lives in local config, so a fresh clone otherwise inherits rules for tools it cannot call. No-ops for projects that never ran `gitnexus setup`. |
| `setup/serena-reconcile.sh` | Keeps Serena usable for the Risk Gate's Python row and the post-`.py`-edit diagnostics call. `--global` makes sure the user-scope `serena` MCP server launches a **pinned PyPI release** with `--open-web-dashboard False`. It registers the server if absent and migrates the old `git+https://github.com/oraios/serena` launch, which re-resolved the git source on every start and timed out on a cold cache. Writes go through `claude mcp`, never by editing `~/.claude.json`. With a project dir, it makes sure `.serena/project.yml` lists every language the repo tracks (`.py` → `python`, `.ts/.tsx/.js/.jsx/.mjs/.cjs` → `typescript`): it creates the file via the pinned `serena project create` when missing, and otherwise appends missing languages, never removing one or touching other keys. Needed because Serena's auto-detection can drop Python, and `.serena/` is gitignored, so the fix can't be committed. It also warns when a project `.mcp.json` launches Serena from git and overrides the pinned server. `--check` is a quiet exit-code probe. Run by `install.sh` (`install_project` and `install_globals`) and `update.sh` (per project, plus `--global` once per sync), always non-fatal. The pinned version lives only in this script (`SDD_SERENA_VERSION` overrides). Tests: `serena-reconcile.test.sh`. |
| `setup/sync-skills.sh` | **Single namer of the two skill tiers.** Installs `skills/` into the user's `~/.claude` split in two: `~/.claude/skills/` is *listed in every prompt* (harness-called skills plus the 14 domain-router "master" skills) and `~/.claude/skill-library/` is reached on demand through a master skill and is **not** listed, so it costs no per-prompt context. The split is driven by `setup/skill-library.txt` (one skill name per line; `#`/blank lines ignored, exact whole-line match). A skill named there installs to `skill-library/` and any stale listed copy is evicted from `skills/`; every other skill installs to `skills/`. `install.sh` and `update.sh` both call it (`sync-skills.sh <harness_dir>`) instead of looping over `skills/` themselves, so the routing lives in exactly one place. Copies are `rm -rf` + `cp -r` per skill, matching `sync_dir` and avoiding BSD `cp` content-dump / GNU double-nesting. No associative arrays — macOS ships bash 3.2. A missing manifest routes **everything** to `skills/` (the pre-split behaviour) and it always exits 0, so it never blocks an install or update. Prints `Skills synced: N listed, M in library`. Tests: `setup/sync-skills.test.sh`. |
| `setup/skill-library.txt` | The manifest read by `setup/sync-skills.sh`, `routines/skill-write.sh` and `routines/skill-delete.sh` — one skill name per line, naming every skill that installs to `~/.claude/skill-library/` instead of the per-prompt-listed `~/.claude/skills/`. See `docs/skills/SKILL-HIERARCHY.md` for the tiering rationale. |

## Daily Maintenance & Evaluation

| Script | Purpose |
|---|---|
| `orchestration/daily-runner.sh` | Per-repo entry point for daily maintenance. Fires `/kiro:daily-maintenance` headlessly. Installed by `install.sh`; triggered nightly by Windows Task Scheduler (WSL) or `session-start-hook.sh` catch-up. |
| `orchestration/daily-orchestrator.sh` | Global orchestrator that iterates all registered projects and calls their `daily-runner.sh`. Before the per-repo loop it runs one harness-level task: a once-per-calendar-day fleet sync that executes `update.sh` so registered projects pick up harness changes without anyone typing anything (nothing else ever ran `update.sh` — `stop-hook.sh` only nudges). Gated by `.last-harness-sync` (day-string compare, no GNU-only `date -d`), guarded by `bash -n update.sh` so a half-written `update.sh` is never run fleet-wide, forwards `--repo`, prints `[would-sync]` under `--dry-run`, and opts out with `SDD_SKIP_HARNESS_SYNC=1`. Its inline drift-review gate does elapsed-days math with `python3`, not `date -d`, and the sweep writes to `$HARNESS_DIR/reports/drift-review-report.md` — the git-ignored `reports/` directory, not `docs/`, so a generated report never lands in tracked documentation. After the per-repo loop (full-fleet runs only, never `--dry-run`) it runs `utils/check-fleet-registration.sh --quiet` and logs any unregistered harness install to `logs/orchestrator.log` / `logs/orchestrator.stderr.log` — a report, never a gate. |
| `orchestration/setup-global-orchestrator.sh` | Register `daily-orchestrator.sh` with Windows Task Scheduler (schtasks). Ends with a **warn-only** preflight: runs `daily-orchestrator.sh --dry-run` through the same `wsl.exe -d <distro> -- bash -lc` path the task uses, and reports if it fails. Warn-only rather than fatal because the matching check (`schtasks /Run` + `LastTaskResult`) verifies Windows-side execution and could not be tested — verify by hand with the `/Query` line the script prints. |
| `orchestration/setup-linux-orchestrator.sh` | Register `daily-orchestrator.sh` with cron (Linux). Exits 1 unless a **preflight** passes: runs `--dry-run` under an approximated cron environment (`env -i`, `PATH=/usr/local/bin:/usr/bin:/bin`), since cron's near-empty environment is where a command that works interactively fails every night invisibly. The preflight also runs on the "already registered" path — that is exactly the state a silently-failing cron job reports. |
| `orchestration/setup-mac-orchestrator.sh` | Register `daily-orchestrator.sh` with launchd (macOS). Wraps the run in `caffeinate -i` so the LaunchAgent's unattended 18:00 fire isn't cut short by idle/display sleep. Exits 1 unless a **preflight** passes: registers a throwaway probe agent (`com.sdd.orchestrator-preflight`) that runs `--dry-run` in the same launchd context, waits up to 30s for its exit code, then boots it out. `launchctl load` returning 0 only proves registration, not that the job can execute — with the harness under `~/Documents` launchd exited 126 (`Operation not permitted`) daily for four days behind a green install. On failure the script names TCC explicitly when `$HARNESS_DIR` is under `~/Documents`, `~/Desktop` or `~/Downloads`, and gives both fixes (move the harness, or grant Full Disk Access to `/bin/bash`). Preflight also runs on the "already loaded" path. |
| `routines/macro-eval-runner.sh` | Runs `/kiro:macro-eval-sweep` headlessly for trend analysis. |
| `routines/harness-health-runner.sh` | Runs the bi-weekly harness health routine: CLAUDE.md review (Phase 1), iterative skill repair (Phase 2), and **token spend attribution (Phase 3)**. The runner executes `utils/token-forensics.py --days 14` itself and substitutes the output into `FORENSICS_PLACEHOLDER` in the prompt, rather than asking the headless session to shell out — a headless run that is merely *told* to run a script can skip it silently, and the phase would then report on nothing while looking like it ran. A missing script or non-zero exit is substituted as a visible marker, so the phase can report "no data" but can never invent figures. Substitution is `sed` for the date and `awk` with an env-var read for the report body, so the captured output's own characters are never interpreted as replacement syntax and a stray `TODAY_PLACEHOLDER` inside it cannot be expanded. Cadence `MIN_GAP_DAYS=13`; force with `HARNESS_HEALTH_FORCE=1`. |
| `routines/skill-curator-runner.sh` | Runs `/kiro:skill-extract` to curate and augment skills from session learnings. Before invoking the prompt, runs `utils/skill-dependency-scan.sh` and substitutes its output into `DEPENDENCY_MAP_PLACEHOLDER` so the sweep can flag cross-referenced skills before proposing delete/merge. |
| `routines/skill-write.sh` | Single source of truth for writing any file inside a skill's directory (`SKILL.md`, a `resources/examples/*.md` file, `eval-verdict.json`, ...). `update.sh`'s sync does `rm -rf` + `cp -r` from `skills/<name>/` (harness source) over `~/.claude/skills/<name>/` (installed) on every scheduled tick — a write landed only on the installed copy of a harness-shipped skill survives until the next sync, then gets silently reverted. Writes source *and* installed together for harness-shipped skills, installed-only for skills with no harness source (marketplace/manually-installed), and takes a pre-write backup to `.claude/memory/skill-repair-backups/<name>/` either way. The installed path depends on the skill's tier: a skill listed in `setup/skill-library.txt` lives in `~/.claude/skill-library/<name>/`, everything else in `~/.claude/skills/<name>/` — writing to the wrong one leaves a stray listed copy and misses the copy Claude actually reads (`setup/sync-skills.sh` is the single namer of the split). `skill-write.sh <skill-name> <new-content-file> [relative-path=SKILL.md]`. Every routine/agent that edits a skill (`harness-health`, `skill-augment-agent`, `skill-curator`) must go through this instead of Write/Edit directly. |
| `routines/skill-delete.sh` | Pairs with `skill-write.sh` for deletes: removes both `skills/<name>/` (harness source) and the installed copy, backing up both first to `.claude/memory/skill-repair-backups/<name>/<timestamp>-deleted/`. The installed path follows the same tier rule as `skill-write.sh` — `~/.claude/skill-library/<name>/` for a skill listed in `setup/skill-library.txt`, `~/.claude/skills/<name>/` otherwise. It also **drops the skill's line from `setup/skill-library.txt`**, so a later sync does not route a skill that no longer exists; the master-router row pointing at it, if any, must still be removed by hand (grep the masters for the name — a dead row is a dangling path, not a crash). Deleting only the installed copy doesn't stick — the same scheduled sync that reverts a partial write recreates a partially-deleted skill from source on its next tick. `skill-delete.sh <skill-name>`. |
| `routines/tool-failure-review-runner.sh` | Promotes recurring tool failures from `.claude/memory/tool-failures.jsonl` into `ERRORS.md` + memory. |
| `routines/security-report-runner.sh` | Daily security scan: runs the security-report prompt headlessly, writes report to `.claude/reports/security/`. Runs at most once per day (`SECURITY_REPORT_GAP_DAYS`). Opt out with `SDD_SKIP_SECURITY_REPORT=1`. |
| `routines/daily-briefing-runner.sh` | Synthesizes a prioritized status digest from `.claude/memory/manager/{projects,people}.md` plus connected live sources (git/GitHub/Jira/Slack), writes it to `.claude/reports/daily-briefings/<date>.md`. Deterministic (no LLM call) bootstrap guard: no-ops with a `-SKIPPED.md` note if neither `projects.md` nor `people.md` exists yet — the ledger is created interactively via `/kiro:daily-briefing`, never fabricated by this headless runner. Self-paces to daily (`DAILY_BRIEFING_GAP_DAYS`). Opt out with `SDD_SKIP_DAILY_BRIEFING=1`. |
| `routines/code-review-learning-runner.sh` | Self-improving code-review learning sweep: compares pr-babysit's logged reviews (`.claude/memory/pr-reviews/pr-<n>.md`) against real human review activity on merged PRs, promotes low-risk findings (conventions, dismissed-flag patterns) straight into memory, and reports higher-risk methodology changes to `docs/code-review-learning-report.md` for human approval. No-ops unless there's a merged+logged PR not yet processed; self-paces to weekly (`CODE_REVIEW_LEARNING_GAP_DAYS`, default 7) once there is. Applies to any repo. Wired into `orchestration/daily-orchestrator.sh` `run_one()`. Opt out with `SDD_SKIP_CODE_REVIEW_LEARNING=1`. |
| `routines/startup-payload-audit.sh` | Deterministic (no LLM) daily audit of the fixed per-session startup token tax (`CLAUDE.md` + `@imports` + `.claude/rules/*` + auto-loaded `MEMORY.md`). Writes `.claude/reports/context/startup-payload.json`, read by the dashboard's Context Health tab. **Ratchet (2026-09-30):** a per-repo ceiling (`startup-payload-ceiling.json`) that only goes down — growth above it is flagged `over_ceiling` with a `delta` and warned on stderr; `--rebaseline` accepts intended growth. The 8000-token budget stays as an absolute cap. `@import` parsing is regex-free (removed from the no-regex debt ledger). Tests: `routines/startup-payload-audit.test.sh`. Self-paces to daily via its own state-file guard. Wired into `orchestration/daily-orchestrator.sh` `run_one()`. Opt out with `SDD_SKIP_STARTUP_AUDIT=1`. |
| `routines/rtk-net-effect-runner.sh` | Deterministic (no LLM) daily wrapper around `utils/rtk-net-effect.py`. Writes `.claude/memory/rtk-net-effect.json`, read by the dashboard's RTK layer to annotate its local-savings figure with a global rerun/reread signal instead of reporting savings alone. Self-paces to daily via its own state-file guard. Wired into `orchestration/daily-orchestrator.sh` `run_one()`. Opt out with `SDD_SKIP_RTK_NET_EFFECT=1`. |
| `routines/hook-config-audit-runner.sh` | Deterministic (no LLM) wrapper around `utils/hook-config-audit.py`. Sweeps the repo's own `.claude/hooks/` and `settings.json`/`.mcp.json` — the harness's own hooks and MCP config, not user content — for secrets (reuses `scan-pii.sh`'s OPF engine), network-exfil patterns in hook scripts, and over-broad permission grants (bare tool name or a `*`-only argument). Neither `hooks/claude/scan-pii.sh` (content-only) nor `hooks/claude/skill-permissions-gate.sh` (fires only on new `SKILL.md` writes) sweeps existing hooks/config. Writes `.claude/reports/security/hook-config-audit.json`. Self-paces to weekly (`HOOK_CONFIG_AUDIT_GAP_DAYS`, default 7). Wired into `orchestration/daily-orchestrator.sh` `run_one()`. Opt out with `SDD_SKIP_HOOK_CONFIG_AUDIT=1`. |
| `validate-behavior-spec.py` | Deterministic (no LLM) structural check for a `.claude/behaviors/<name>/BEHAVIOR.md` spec: file exists, frontmatter has `name`/`description`, `name` matches the parent directory. Called by `behavior-spec-agent` (`/kiro:daily-maintenance` Step 6b) after drafting or revising a spec; never run standalone. |

## Session Intelligence

> **No regex anywhere in this tree.** `ruff.toml` bans importing `re` (TID251). Every
> pattern match was replaced with an explicit parser on 2026-08-20 after `(\d+)%` read
> "24.5%" as 5 and the dashboard showed a wrong number for weeks without erroring. When
> a value has to be read back by a program, emit it as structured data at the source —
> `session/record_metric.py` is the reference for that.

| Script | Purpose |
|---|---|
| `detect_reexplanation.py` | Haiku-based session signal detector. Classifies sessions as drain (re-explanation) or charge (approval). Called by `hooks/claude/stop-hook.sh`. Runs Haiku through `claude --print` (subscription auth), **not** the `anthropic` SDK — the SDK needs a separately-billed `ANTHROPIC_API_KEY`, and with none set it failed silently on every session, which the dashboard rendered as "0 memory gaps". Sets `SDD_HEADLESS=1` on the child so the stop hook skips the detector and does not recurse. On failure it emits a `[detector-down]` observation and exits 4 — never a silent zero. |
| `record_metric.py` | Appends one measurement to `.claude/memory/metrics.jsonl` (`session-quality`, `keep-rate`, `memory-gap`). The dashboard reads this file and never re-extracts numbers from prose in `observations.md`. Same day + same metric replaces rather than appends. `--idle` marks routine windows with no user session so they are excluded from averages. Called by the `session-quality` and `keep-rate` skills and by `detect_reexplanation.py --record-metric`. |
| `micro_reflect.py` | Extracts durable facts from drain sessions → writes `[auto-learn]` entries to `hot-memory.md`. Can be invoked standalone on drain signals. |
| `trust_score.py` | Applies the Judge score delta to the trust score line in `hot-memory.md`. **`apply --delta` is repeatable** (2026-09-03): `/kiro:daily-maintenance` runs `session-judge` 3× and passes all three, and the helper applies the **median** so a single outlier draw cannot move a cumulative score. When the samples spread by more than `JUDGE_SPREAD_LIMIT` (2.0 on the ±4.5 scale) the day is recorded `inconclusive` with delta `0.0` — a reading that depends on which draw you looked at is not a reading. Raw `samples`, `spread` and `inconclusive` are persisted to `trust-score.jsonl` so an inconclusive day is distinguishable from a day nothing ran, and the dashboard's Trust Battery renders a `⚠ judge split` badge for it. A single `--delta` still works and reports `"spread": null`, not `0.0` — one sample has no spread and claiming otherwise would read as perfect agreement. `auto-score` is unchanged and deliberately single-sample: it counts tags in `observations.md`/`metrics.jsonl` and is deterministic, so there is nothing for the spread gate to measure. Tests: `session/trust_score.test.sh` (24 offline cases). Sources: Perrone's `pass^k`, VVAH's majority-vote FP filtering. |
| `session/_archive_obs.py` | Moves whole dates out of `.claude/memory/observations.md` into `.claude/memory/glacier/observations-<today>.md`. Selection is **by date, never by count** — the keep-most-recent-N rewrite reads the file, decides what to keep, and rewrites it whole, so an entry appended between the read and the write is destroyed (that race destroyed an entry on 2026-09-01). Archiving a fixed set of *past* dates commutes with a concurrent append: today is refused outright, so a same-day append can never be in the selected set. `--dates` is required; `--dry-run` reports without writing. Called by the `housekeeping-agent`. |
| `session/_keep_rate_calc.py` | Keep Rate calculator — the pinned recipe from `skills/keep-rate/SKILL.md` Step 2, extracted so the figure is reproducible instead of re-derived per run. Keep Rate = lines a Claude-co-authored commit added that are still attributable to it in `HEAD`, over all lines it added: a durability signal, not a correctness one. The pinned choices (working branch only + `--no-merges`, one `HEAD`-wide blame map keyed by commit so lines that moved to a renamed file still count, `-M -C` on blame and numstat, `--line-porcelain`, binariness tested on the working-tree file, empty-tree base for root commits, denominator spanning every text path a commit touched, per-commit credit clamped to lines added) are what make two readings comparable — change one and record the basis alongside the value. `--days`, `--repo`, `--json`. |
| `session/write_handoff.py` | Deterministic (non-LLM) transcript-to-markdown session handoff. Reads the transcript path from stdin JSON, extracts branch/cwd/recent messages, writes `.claude/memory/handoff/latest.md`. Invoked with `--trigger precompact` from `compaction-discipline-hook.sh`, `--trigger agent-spawn` from `gbrain-agent-spawn.sh`, and `--trigger cache-cost` from `stop-hook.sh` when cache tokens hit ≥70% of session spend after ≥1 compaction; surfaced (if <24h fresh) by `session-start-hook.sh`. Never invoked manually. |

## PR Automation

| Script | Purpose |
|---|---|
| `pr/detect_base_and_create.sh` | Shared logic behind PR-babysitting automation. If a `gh-stack` is already active for the branch (`.git/gh-stack` exists — see the `stacking-pull-requests` skill), runs `gh stack submit --auto` for the whole stack instead and exits, skipping the single-PR path below. Otherwise: auto-detects a feature branch's true fork-point base (via `git merge-base` + most-recent-commit-date comparison across all local/remote refs, falling back to the repo's default branch) and idempotently opens a draft PR (`gh pr create --fill --draft`) if one isn't already open.
